## 2. Critical finding — `PUBLIC_SITE_URL` env-var dependency

### What the code does

`api/verify-payment.js:25-35`:
```js
function getPublicSiteOrigin() {
  const explicit = process.env.PUBLIC_SITE_URL || process.env.VITE_PUBLIC_SITE_URL;
  if (typeof explicit === 'string' && explicit.trim().length > 0) {
    return explicit.replace(/\/$/, '');
  }
  const vercel = process.env.VERCEL_URL;
  if (typeof vercel === 'string' && vercel.trim().length > 0) {
    return `https://${vercel.replace(/\/$/, '')}`;
  }
  return 'https://www.sealedvow.com';
}
```

This computes the origin used for the share link embedded in the email. Three resolution tiers, in order.

### Why this is a critical operational concern

`grep -rn "PUBLIC_SITE_URL"` across the entire codebase returns ZERO matches outside `api/verify-payment.js:26`. **This is a NEW env var introduced by this PR with no documentation, no .env.example update, no Vercel admin configuration step bundled in.**

Behavior matrix without `PUBLIC_SITE_URL` set:

| Environment | `VERCEL_URL` value | Resulting share-link origin in email |
|---|---|---|
| Vercel production | `sealedvow-XXXXX.vercel.app` (deployment-specific) | `https://sealedvow-XXXXX.vercel.app/<slug>` |
| Vercel preview | `sealedvow-git-BRANCH.vercel.app` (preview-specific) | `https://sealedvow-git-BRANCH.vercel.app/<slug>` (and Vercel's preview SSO gate would 401 receivers) |
| Local `vercel dev` | unset | `https://www.sealedvow.com/<slug>` (hardcoded fallback) |

### Real-world consequence in production

If `PUBLIC_SITE_URL` is not set in Vercel production env, every paid customer's email will contain a deployment-specific URL like `https://sealedvow-i4myph90x-vowstudioapps-projects.vercel.app/abc--xyz--12345678` instead of `https://www.sealedvow.com/abc--xyz--12345678`. This is:

1. **Brand-incoherent** — receivers see a Vercel-branded URL, not a Sealed Vow-branded one. Reduces trust in the link being legitimate.
2. **Per-deploy churn** — every deploy generates a new `VERCEL_URL`, so emails sent from successive deploys use different origins (though all functionally route to the same SPA).
3. **Forwarding/sharing risk** — a deployment URL pasted in social/email screenshots looks like a staging link, not a production one.

The hardcoded final fallback (`https://www.sealedvow.com`) only fires if `VERCEL_URL` is also unset, which on Vercel is essentially never.

### Mitigation (not for me to apply — flagging only)

Setting `PUBLIC_SITE_URL=https://www.sealedvow.com` in Vercel production env (and `https://www.sealedvow.com` or appropriate preview URL in Preview env) makes the code behave correctly. This is an OPS task, not a code task.

### Secondary observation — `VITE_PUBLIC_SITE_URL` server-side read

`getPublicSiteOrigin()` also reads `VITE_PUBLIC_SITE_URL`. Vite-prefixed env vars are CONVENTIONALLY frontend-only (they're exposed to the bundle via `import.meta.env`). Reading one server-side from `process.env` in a Node serverless function is unusual but functional (Vercel loads all env vars into `process.env` regardless of prefix). Worth flagging as a code-style smell — a future maintainer might assume `VITE_*` is never read server-side and prune it without checking.

## 5. Visual artifact — back-to-back hairlines

### What happens

When `receipt` is provided, the rendered HTML structure (lines 298-313 + the inlined `${receiptHtml}`) produces:

```
[ privacy line: "Only the person you choose..." ]
                    ↓ margin: 32px below
[ TOP HAIRLINE — share-link block start ]
[ "Your share link:" + URL paragraph ]
                    ↓ margin: 24px below
[ BOTTOM HAIRLINE — share-link block end ]
                    ↑ ZERO vertical space ↓
[ TOP HAIRLINE — receipt block start ]
                    ↓ margin: 24px below
[ Amount / Payment ID / Date paragraphs ]
[ BOTTOM HAIRLINE — receipt block end ]
                    ↓ margin: 32px below
[ "Thank you. This was something..." ]
```

The two hairlines between the share-link block and the receipt block are **stacked back-to-back with no spacer between them**. They will render as a single thicker gold line (or, depending on email client rendering, two visibly distinct adjacent lines), not the intended single hairline punctuation.

### Why this happens in code

Looking at `sendEmail.js:298-313`:
```js
              <!-- Share link — always present (PR-46.5). Visually separated from optional receipt below. -->
              <table ...border-top: 1px solid GOLD_HAIRLINE_RECEIPT...>
                <tr><td font-size:0;line-height:0;height:0...>&nbsp;</td></tr>
              </table>

              <p>Your share link:</p>
              <p><a>...</a></p>

              <table ...border-top: 1px solid GOLD_HAIRLINE_RECEIPT...>  ← share-link bottom hairline
                <tr><td font-size:0;line-height:0;height:0...>&nbsp;</td></tr>
              </table>
              ${receiptHtml}    ← receipt-block top hairline immediately follows
```

When `receiptHtml` expands, its first element is a `<table>` with the same `border-top` hairline. Two consecutive `<table>` elements with `border-top` hairlines, separated by no margin or spacer rows, create the back-to-back artifact.

### Severity

**Moderate.** Doctrine Risk #8 mitigation called for visual separation between the share link and the receipt block, and structurally that separation IS there (two hairlines = a visible boundary). But the implementation produces a visual register the doctrine wouldn't have intended — a "thicker" line at the boundary rather than a single-hairline beat.

In email clients that ignore zero-height table rows (some do, some don't), the artifact may render slightly differently. Most modern email clients (Gmail, Apple Mail, Outlook 365) will show this as two adjacent lines. Some older clients may collapse them.

### Not a doctrine violation

The doctrine doesn't specify HOW the visual separation is achieved. The implementation has a separation; it's just not a polished one. Flagging as a polish concern, not a doctrine breach.

### Suggested verification

Manual visual review of the rendered email (auth-paid path, in Gmail) before merging to main. The fix would be a one-line CSS adjustment (omit one of the duplicate hairlines, or add a small margin between them) — out of scope for this audit.

## 8. Idempotency-on-replay semantic check

### What changed from PR-46

PR-46's helper returned `void` and short-circuited silently on idempotency hit. PR-46.5's helper returns `Promise<{ delivered: boolean }>` — so the idempotency-hit case now needs a deliberate `delivered` value.

### Cursor's choice

`verify-payment.js:140` returns `{ delivered: true }` when the idempotency record exists.

### Analysis

**Semantically defensible** under the framing "is the share link in the user's inbox?" — the user's inbox DOES contain the email from a prior request, so `delivered: true` is honest about the END STATE.

**But could be misread** under the framing "did THIS request send a new email?" — under this reading, idempotency-hit should report `delivered: false` because no new send happened.

The `emailDelivered` flag flows to SHARE screen → drives the "We also sent your share link to your email." line. From the SHARE screen's perspective, the user wants to know "should I expect an email?" — for which the answer IS yes (the prior send is in their inbox). So Cursor's choice aligns with the user-facing contract.

### Edge case

The idempotency check happens BEFORE the email-source resolve. So if a user pays once successfully (Razorpay path, sessionUser.email available, emailDelivered: true), then the SAME paymentId hits verify-payment again with NO authenticated session AND NO `recipientEmail` (e.g., from a webhook retry without session cookies)... the idempotency hit returns `delivered: true` correctly because the original email DID get delivered. This is correct.

But: if a user pays as guest and provides recipientEmail "alice@example.com", and a later replay arrives with recipientEmail "bob@example.com" (different value, somehow), the idempotency hit returns `delivered: true` and notifications/{paymentId}.recipientEmail still shows "alice@example.com". The replay's new email value is never persisted or used. Acceptable behavior — but worth knowing this edge case exists.

**No action needed; flagging for awareness.**

## 9. Replay-path `emailDelivered` query

### What it does

verify-payment.js:567-575 — when a replay 200 is returned (claim transaction found existing record), Cursor added a synchronous RTDB read to determine `emailDelivered`:

```js
let emailDelivered = false;
try {
  const nSnap = await adminDb.ref(`notifications/${razorpay_payment_id}`).once('value');
  const nv = nSnap.val();
  if (nv && typeof nv === 'object' && nv.resendMessageId) {
    emailDelivered = true;
  }
} catch {
  emailDelivered = false;
}
return res.status(200).json({
  verified: true,
  replay: true,
  ...
  emailDelivered,
});
```

### Analysis

**Correct semantics.** A replay request needs to return the same `emailDelivered` the original request returned, otherwise the SHARE screen state would diverge between the original payer and any later replay.

**Tiny perf cost.** One extra RTDB read on the replay path. Negligible — replays are rare (only on retry/double-submit).

**Defensive try-catch:** if the read fails, defaults to `emailDelivered: false`. That's the safer fallback (won't over-promise email delivery).

✓ No issues.
