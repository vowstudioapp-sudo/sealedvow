## 1. Executive summary

PR-46.5 requires four classes of change, all CSS-bounded inside the existing post-payment fulfillment pipeline:

1. **Capture surface** — add an optional email field to `SignInPromptModal` (variant === 'payment'), thread the value through `runOrPromptSignIn` → `safeSetStage(AppStage.PAYMENT)` → `PaymentStage` → `verify-payment` request payloads.
2. **Fulfillment pipeline** — accept `recipientEmail` in `verify-payment.js`'s razorpay request body AND founder request body; pass through to `sendLetterSealedNotification` as a fallback when `sessionUser.email` is absent.
3. **Email rendering pipeline** — restructure `lib/email/sendEmail.js` so the share link is unconditionally rendered and the receipt block is conditionally included. PR-46's existing call site keeps working without conditional logic.
4. **SHARE-screen messaging** — surface a quiet line on success-with-email-delivered. Delete the dead landing-page placeholder.

**Highest-risk implementation area:** the email rendering pipeline restructure (Section 5). This modifies a production-validated artifact (PR-46's locked email template). The restructure must keep the receipt block byte-identical for the authenticated path while introducing the share-link block, all without changing the helper's idempotency contract or the call site's signature. Risk class: **moderate-low** (deterministic, testable) but worth careful sequencing.

**Two architectural traps surfaced** during this scoping pass that look deceptively simple:

A. **Founder-flow capture surface symmetry is real but conditional.** Founder users DO traverse `runOrPromptSignIn` at the Preview→Payment transition, which means the email field appears for them. But the founder-code submission inside `PaymentStage.tsx` does NOT thread the captured email into its `verify-payment` POST body — that's a separate code path from the Razorpay flow. **The doctrine's symmetry claim holds at the UI layer; the data plumbing requires explicit founder-path wiring.** See Section 7.

B. **`onPaymentComplete` callback shape change is breaking.** The callback currently returns `{ replyEnabled, sessionKey, shareSlug }`. To surface email-delivery success on SHARE screen, the callback must additionally carry `emailDelivered: boolean` (or equivalent). Two callers in App.tsx both consume this shape — both need updating in lockstep. See Section 4.

## 4. Proposed payload / data-flow changes

### 4.1 New request body shape — verify-payment.js

**Razorpay branch (was):**
```json
{
  "razorpay_order_id": "...",
  "razorpay_payment_id": "...",
  "razorpay_signature": "...",
  "coupleData": { ... },
  "requestId": "..."
}
```

**Razorpay branch (PR-46.5):**
```json
{
  "razorpay_order_id": "...",
  "razorpay_payment_id": "...",
  "razorpay_signature": "...",
  "coupleData": { ... },
  "recipientEmail": "user@example.com",   // optional, new
  "requestId": "..."
}
```

**Founder branch (was):**
```json
{
  "paymentMode": "founder",
  "founderToken": "...",
  "coupleData": { ... }
}
```

**Founder branch (PR-46.5):**
```json
{
  "paymentMode": "founder",
  "founderToken": "...",
  "coupleData": { ... },
  "recipientEmail": "user@example.com"    // optional, new
}
```

**Validation:** treat `recipientEmail` as a string OR absent. If present, sanity-check it via a lightweight regex (e.g., `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) before passing to the helper. Don't use Zod for this — it's a transport-layer field, not part of the `CoupleData` schema. Per doctrine, **email never lives in CoupleData.**

### 4.2 New `onPaymentComplete` callback shape

**Was:**
```ts
onPaymentComplete: (result: {
  replyEnabled: boolean;
  sessionKey: string;
  shareSlug: string;
}) => void
```

**PR-46.5:**
```ts
onPaymentComplete: (result: {
  replyEnabled: boolean;
  sessionKey: string;
  shareSlug: string;
  emailDelivered?: boolean;   // NEW — true iff verify-payment confirmed Resend success
}) => void
```

**Source of `emailDelivered`:** verify-payment.js return body must add an `emailDelivered: boolean` field. Read from the same Resend success that is already captured into `notifications/{paymentId}.resendMessageId`. Helper currently sets resendMessageId locally; we need it to also surface a return value to the caller (currently helper returns `void`).

**Helper signature change:**
```js
// Was: async function sendLetterSealedNotification({ sessionUser, sanitized, paymentId, amountPaise, requestId }) → void
// PR-46.5:
async function sendLetterSealedNotification({
  sessionUser,        // unchanged
  sanitized,          // unchanged
  paymentId,          // unchanged
  amountPaise,        // unchanged — controls receipt block inclusion
  recipientEmail,     // NEW — fallback when sessionUser.email absent
  shareUrl,           // NEW — share URL to embed in email body
  requestId,          // unchanged
}) → Promise<{ delivered: boolean }>
```

**Caller update (verify-payment.js return):**
```js
// At the razorpay return + founder return:
const emailResult = await sendLetterSealedNotification({...});
return res.status(200).json({
  verified: true,
  sessionKey,
  shareSlug,
  replyEnabled,
  paymentId,
  emailDelivered: emailResult.delivered,   // NEW
});
```

### 4.3 New `notifications/{paymentId}` schema

**Was:**
```js
{
  letterSealedSentAt: <ISO timestamp>,
  resendMessageId: <id>
}
```

**PR-46.5:**
```js
{
  letterSealedSentAt: <ISO timestamp>,
  resendMessageId: <id>,
  recipientEmail: "user@example.com"     // NEW — store the email actually used
}
```

**Why store the email here, not on payments/{paymentId}:** Q2 resolution. Operational value for support: "given a paymentId, which email did we attempt delivery to?" answers the recovery-by-paymentId question without requiring inbox lookups.

### 4.4 Helper guard restructure

**Current guards (post-PR-46 amendment):**
1. Guard 1 — `!sessionUser?.email` → skip (no source of email)
2. Guard 2 — `amountPaise <= 0` → skip (founder no-receipt — but founder is no longer called by amendment)
3. Guard 3 — idempotency check on `notifications/{paymentId}` → skip if already sent

**New guards (PR-46.5):**
1. Guard 1 — Resolve effective email: `const email = sessionUser?.email ?? recipientEmail ?? null`. If `email === null`, skip (no source). Log: `[Verify] Email skipped — no email source (auth or guest-provided)`.
2. Guard 2 — *removed.* Founder path now sends email when `recipientEmail` provided. The conditional-receipt logic moves into the renderer (Section 5).
3. Guard 3 — idempotency check unchanged.

**Note:** Guard 2's removal is the moment when the founder branch starts calling the helper again. This must be paired with the new founder-branch helper call in verify-payment.js (Section 3.3).

## 5. Rendering architecture analysis

### 5.1 Current state recap

`buildLetterSealedEmail` (lines 197-320) is a single pure function returning `{ subject, html, text }`. It accepts `{ senderName, formattedAmount, paymentId, formattedDate }` and:
- Always renders the receipt block (Amount / Payment ID / Date).
- Never renders a share link.
- Subject: `"Your letter has been sealed."`

### 5.2 Required restructure

**New signature:**
```js
buildLetterSealedEmail({
  senderName,
  shareUrl,           // NEW — required
  receipt,            // NEW — optional { formattedAmount, paymentId, formattedDate }
})
```

**New rendering logic:**
1. **Top of body (always):** greeting + "Your letter has been sealed."
2. **Share-link section (always):** new prominent block — share URL rendered as a clickable link AND as plain copy-paste text. Editorial register (gold hairline above + below, calm copy, no marketing language).
3. **Receipt block (conditional):** if `receipt` is provided, render the existing Amount / Payment ID / Date block beneath the share-link section.
4. **Closing (always):** existing `Thank you. This was something that mattered enough to be written properly.` + `— Sealed Vow` + tagline.

**Plain-text fallback (parallel structure):** mirror exactly. Share link as a bare URL with a leading line "Your share link:".

**Caller-controlled vs renderer-controlled:**
- Caller (sendLetterSealedNotification helper) decides WHETHER `receipt` is passed (based on `amountPaise > 0`).
- Renderer (buildLetterSealedEmail) decides HOW to render (always share link; conditional receipt).
- This keeps the conditional logic in ONE place — the renderer — and the caller just provides data.

**No parallel template, no new exported function.** The directive's rendering-architecture constraint is satisfied: composable blocks within a unified pipeline.

### 5.3 Receipt block visual separation (doctrine Risk #8)

The doctrine flags the email-forwarding privacy risk: a signed-in user may forward the receipt to an accountant; the share link goes with it. Mitigation: visually separate the receipt block from the share-link block so the user can screenshot/copy the receipt portion alone.

**Implementation implication:** in the new HTML, the receipt block should sit BELOW a clear visual divider after the share-link block. The share-link block and receipt block should be independently selectable in a screenshot. Specifics are template-level and belong in implementation, not scoping — but the structural ordering (share link first, receipt second, separated by a hairline) is a scoping decision.

### 5.4 Idempotency contract preservation

The current idempotency record key (`notifications/{paymentId}.letterSealedSentAt`) is unchanged. Adding `recipientEmail` is additive. The check-then-set pattern at verify-payment.js:127-186 is unchanged.

**Resend-message-id semantics:** the helper currently captures `resendMessageId` from `sendResult.id` and persists it. PR-46.5 should also use `sendResult.ok` as the source of truth for `emailDelivered: boolean` returned to the caller. This is already available at verify-payment.js:158 (`sendResult.ok !== true` → log error and return). One-line change: capture the boolean and return it.

## 6. Risk analysis

### 6.1 Link-preview / prefetch safety audit (REQUIRED per directive)

**Question:** Does embedding the share link in an email create a risk that link-preview crawlers (WhatsApp, iMessage, email clients, social bots) accidentally consume tokens, trigger analytics, or mark the letter as opened?

**Audit findings:**

| Surface a crawler hits | Behavior | Risk? |
|---|---|---|
| `https://www.sealedvow.com/<shareSlug>` (HTML root) | `vercel.json` SPA rewrite serves `index.html` + JS bundle. Crawler doesn't execute JS. Returns static HTML shell. | None |
| `POST /api/load-session` | Crawlers issue GET, not POST. `guardPost(req, res)` returns 405 immediately. Even if crawler attempts POST, the endpoint is read-only (no writes). | None |
| `POST /api/letters/mark-opened` | Same — POST-only, gated by user interaction inside the SPA (envelope-open animation completion). Crawlers cannot trigger. Endpoint is also idempotent (line 43-45 short-circuit if already opened). | None |
| Open Graph meta tags in `index.html` | Currently no OG tags exist for the receiver route (verified via grep on `<meta property="og:`). Even if added later, OG fetch is GET-only. | None |

**Conclusion:** **The current architecture is safe for share-link prefetch by all major link-preview engines.** The two state-mutating endpoints (`mark-opened`, `verify-payment`) are POST-only AND gated by user interaction. The receiver SPA is a static HTML shell at the network level; mutations only occur when the actual receiver interacts with the experience.

**No implementation work required for prefetch safety.** This is one of the deceptively-simple surfaces that turned out to be already safe by virtue of the existing POST-only-API + SPA-shell architecture.

**Caveat for implementation review:** if PR-46.5 adds any new GET endpoints under `/api/` that read or write state for the receiver flow, this audit must be re-run. Current scope does not introduce such endpoints.

### 6.2 Email-forwarding privacy risk (doctrine Risk #8)

Already addressed in Section 5.3 — visual separation of receipt from share link in the new template structure.

### 6.3 Identity-confusion risk (doctrine Risk #1)

The bypass-moment email field MUST carry copy that explicitly disambiguates "delivery destination" from "account creation." This is a copy decision at implementation time, but the scoping constraint is: the input field cannot be UNLABELED, and labels like "Email" or "Email address" are insufficient — they imply account semantics. Acceptable label patterns per doctrine: `"Optional — we'll send the share link here. No account created."` Final wording is implementation-level; the scoping requirement is that bare "Email" is forbidden.

### 6.4 Concurrent-send race (already mitigated)

The doctrine documents this in PR-46's idempotency note: best-effort single-check-then-set leaves a small window for duplicate sends if two webhook retries fire concurrently. PR-46.5 doesn't change this — the new `recipientEmail` field is written in the same transaction as `letterSealedSentAt`, so either both land or neither does. **No new race surface introduced.**

### 6.5 Payload-size growth

Adding `recipientEmail` to verify-payment request body: ~30-100 bytes. Negligible. Same for `emailDelivered` boolean in response: negligible. No payload-size threshold breached.

### 6.6 Existing-user regression risk (PR-46 already-shipped)

PR-46's authenticated-user email behavior must remain byte-identical for the receipt content. The restructure changes the rendering pipeline but the receipt block must continue to render IDENTICAL HTML (and text) for inputs that match the PR-46 call shape. **Acceptance criterion for implementation:** snapshot test or manual screenshot diff against the production-rendered PR-46 email.

The share-link block is NEW for authenticated users too — PR-46 didn't include it. This is the doctrine's intentional change (Q-new) but it IS a behavior change for the production-validated PR-46 path. Worth flagging in implementation verification.

### 6.7 Founder-flow first-call risk

PR-46's amendment removed the founder-path helper call. PR-46.5 puts it back (with `recipientEmail` threading). **This is the FIRST production helper invocation for the founder path.** No prior production data exists for founder-path Resend behavior. Implementation should treat the first founder-code redemption post-deploy as a verification gate, similar to PR-46's E2E test.

```
              ├─ user clicks "Send letter" → handlePay() → Razorpay flow
              └─ user clicks "Have a private access code?" → handleFounderCode() → founder flow
```

Both populations land on PaymentStage AFTER traversing the modal. The captured `guestEmail` (new state) is therefore available to BOTH `handlePay` and `handleFounderCode` because both live in the same PaymentStage component instance.

### 7.3 Where the symmetry breaks (data-plumbing gap)

The doctrine's UI-symmetry claim is correct, but a separate engineering reality must be acknowledged: **the founder branch in PaymentStage does not currently include any conduit for additional fields in its verify-payment POST body.** Specifically:

- `handleFounderCode` (PaymentStage.tsx:69-117) constructs its verify-payment payload at line 95-99 with only `{ paymentMode, founderToken, coupleData }`. Adding `recipientEmail` here is a small change (one line) but it IS a change — the founder path doesn't inherit it for free.
- `verify-payment.js` founder branch (lines 297-413) doesn't currently destructure or use any `recipientEmail`. Wiring it through the helper requires explicit founder-branch code (Section 3.3).

### 7.4 Conclusion

**Doctrine claim is sound at the philosophy layer (Q1 resolution stands).** The founder path traverses the same email-capture surface and so naturally inherits the email field at the UI layer. **But the data plumbing requires explicit founder-path wiring** in two files (PaymentStage.tsx and verify-payment.js). Scoping does not flag this as a doctrine-touch question — the doctrine doesn't claim the data plumbing is automatic, only that the capture surface is shared. Implementation just needs to thread the value end-to-end on both paths.

## 9. Open implementation questions

These are engineering-translation questions raised by the codebase reading. None are doctrine-touch questions. If any escalates into a philosophy issue, it needs to be flagged separately to you for doctrine amendment.

### O-1 — Email field placement inside SignInPromptModal

The modal currently has two buttons (Continue with Google, Continue as Guest). Adding an email field has multiple placement options:
- (a) Below "Continue as Guest" only (visible only after the user has visually committed to bypass)
- (b) Above "Continue as Guest" with a sub-label "Optional — only if you continue as guest"
- (c) Below the Google button with a label that disambiguates "If you continue as guest, we'll send your share link here. Sign-in users get this automatically."
- (d) Inside an expanded section that only renders when the user starts to interact with the bypass button (progressive disclosure)

Doctrine constraint: copy must satisfy the truthfulness principle. All four are doctrine-compliant if labeled correctly. Choice is UX-level — implementation prompt should pick one with reasoning, not blindly follow an option here.

**Recommended: (c)** — keeps the field always visible (no progressive disclosure tax for users who want to provide it), explicitly disambiguates from sign-in semantics, and respects the modal's compact existing layout.

### O-2 — Should email field validation be client-side, server-side, or both?

The transport-layer field doesn't go through Zod (per Section 4.1). Question: should the modal validate email format client-side before allowing "Continue as Guest", or accept any string and let server-side Guard 1 silently skip on malformed addresses?

Doctrine constraint: helper never throws, never blocks fulfillment. So invalid emails MUST gracefully no-op server-side. But UI hygiene suggests client-side format hint is good practice.

**Recommended: light client-side regex validation as a UI hint (red border on malformed input) but DO NOT block the Continue-as-Guest button.** Server-side helper does its own sanity check and silently falls through to Guard 1 on malformed input.

### O-3 — Razorpay `prefill.email` pre-fill UX

If we capture an email at the modal, should we pass it to Razorpay's `prefill.email` so the Razorpay payment modal auto-fills it?

Doctrine doesn't address this. It's a small UX nicety. Risk: Razorpay then captures the email in their system too, which has implications for accounting / customer records.

**Recommended: YES — pass `prefill.email`. Razorpay already captures customer-provided email anyway as part of payment flow; prefilling is a convenience that aligns the user-provided email with what Razorpay already collects.** But flagged because it's a tiny doctrine-adjacent decision.

### O-4 — Where to reset `guestEmail` state on stage transitions

`guestEmail` lives in App.tsx-level state. When does it reset?
- On exit from PAYMENT/SHARE stages? (Reasonable default.)
- On start of a new letter-creation flow? (Yes, definitely.)
- On sign-in mid-flow? (Could either keep — sign-in user might still want delivery to this address — or discard — since auth provides authoritative email.)

**Recommended: clear on exit from SHARE stage AND on every entry to PREPARE stage. On sign-in mid-flow, KEEP the guestEmail in state — the sender may have provided a different email than their Google account, and the explicit guest-provided value should win.** But this is judgment; flagged.

### O-5 — Helper return-value contract evolution

PR-46's helper returns `void`. PR-46.5 needs it to return `{ delivered: boolean }`. Is this a breaking change for any other caller?

Codebase grep: `sendLetterSealedNotification` is called only in `api/verify-payment.js` (verified — single call site post-amendment). No external callers. **Safe to change return type.**

### O-6 — Notification-record write timing

Doctrine Q2 resolution stores `recipientEmail` on `notifications/{paymentId}` alongside `letterSealedSentAt` and `resendMessageId`. Question: when does the write happen for the **founder path**, given the founder path's amount is 0 and historically didn't write a notifications record at all?

Two options:
- (a) Write `notifications/{paymentId}` only when an email is actually sent (existing behavior, plus the new `recipientEmail` field).
- (b) Write `notifications/{paymentId}` on every successful seal, with `letterSealedSentAt: null` if no email was sent (so support can always look up paymentId → email-sent? state).

**Recommended: (a).** Continues the existing semantics — `notifications/` records the existence of a notification, not the absence. Operational lookups for "was an email sent?" become a presence-of-record check, which is cleaner.

But implementation prompt should explicitly choose, since the founder path is the new caller introducing this question.

### O-7 — Test plan for the rendering pipeline restructure

Risk #6.6 requires verification that the receipt-block portion of the email renders byte-identical to PR-46's production output. How is this verified?
- Snapshot test (would require introducing test infrastructure — none exists in repo per CLAUDE.md "no test runner").
- Manual diff (compare a rendered HTML output against a stored PR-46 baseline).

**Recommended: manual diff against a stored baseline HTML for the test-stub inputs (same stubs PR-45 used in api/test-email.js, before that endpoint was deleted in PR-45.5). Since the test endpoint is gone, the implementation prompt may need to add a one-off node script — or run buildLetterSealedEmail against the stubs and inspect output.** This is implementation-tactics-level, but worth flagging as a gate before merge.
