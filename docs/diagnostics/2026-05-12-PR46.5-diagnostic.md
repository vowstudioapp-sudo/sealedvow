# PR-46.5 Diagnostic — Guest Checkout & Trust Architecture

**Date:** 12 May 2026
**Author:** Claude Code (read-only diagnostic)
**Scope:** Sender-side guest checkout flow, founder-code path, trust-architecture surfaces
**Status:** Diagnostic only — no design, no implementation

## Summary

The sender path from landing through sealed letter payment is largely **auth-optional** at the API layer: `api/create-order.js` never resolves session, and `api/verify-payment.js` resolves `getSessionUser` as optional and provisions the sealed letter in RTDB for guests and signed-in senders alike. The **primary client gate** before payment is a **soft sign-in prompt** (`runOrPromptSignIn` in `App.tsx`): guests can continue via **Continue as Guest** in `SignInPromptModal.tsx`, after which `PaymentStage.tsx` runs without inspecting auth. Post-payment **letter-sealed email** is implemented only on the **paid Razorpay branch** via `sendLetterSealedNotification` in `api/verify-payment.js`; it **skips guests** at Guard 1 and **is not invoked at all** on the **founder-code** fulfillment branch. **`shared/{sessionKey}`** holds the letter payload and optional `senderUid`; there is **no sender email field** on `CoupleData` in `types.ts`, and **no server-side store** ties a guest’s identity to their share link beyond payment/session records. **`SharePackage.tsx`** surfaces the share URL only in client state after verification; **`clearPreparationDraft`** runs on success, and **`SHARE`** is outside persistable draft stages, so **in-tab state loss** after payment maps to **no client-side recovery** of the link from this codebase alone.

### 2. `PaymentStage.tsx` and auth state

- **Does not gate** payment on auth: no `useAuth`, no session checks (`components/PaymentStage.tsx:46–371`).
- **No different UI** for guest vs authenticated users; the only mode branch is **`isEidFlow`** (`data.occasion === 'eid'`) for pricing breakdown and **`customAmountPaise`** on create-order (`components/PaymentStage.tsx:60–63`, `141–146`).
- **Razorpay prefill** uses `data.senderName` only (`components/PaymentStage.tsx:186`), not account email.

### 3. `api/create-order.js` and auth

- **No `getSessionUser` import or call** in the file (`api/create-order.js:1–272`).
- **Guest order creation:** normal Razorpay path accepts POST body with optional `customAmountPaise` (`api/create-order.js:92`, `177–193`, `258–266`).
- **Founder path:** accepts `founderCode`, runs `founderTransaction`, mints `founderToken` (`api/create-order.js:97–174`).
- **Identifying information required:** none for identity; only payment/founder parameters as above.

### 4. `api/verify-payment.js` and auth (success path / email)

- **Session resolution:** `const senderSessionUser = await getSessionUser(req);` and `const senderUid = senderSessionUser?.uid || null;` (`api/verify-payment.js:283–287`). Comment states guests are supported (`api/verify-payment.js:283–285`).
- **Paid Razorpay success path** (after successful multi-path write and `markActiveDraftCompleted`): `await sendLetterSealedNotification({ sessionUser: senderSessionUser, ... })` (`api/verify-payment.js:689–700`).
- **`sendLetterSealedNotification` — Guard 1 (no authenticated sender email):** `if (!sessionUser || !sessionUser.email) { ... return; }` (`api/verify-payment.js:93–101`). This is the **silent skip** for guests documented in PR-46.
- **Scope note for PR-46 wording “only auth-dependent branch”:** Inside **`sendLetterSealedNotification`**, auth affects the skip/send decision only through **Guard 1** (`api/verify-payment.js:93–101`); **Guard 2** is amount-based (`api/verify-payment.js:103–111`), **Guard 3** is idempotency (`api/verify-payment.js:113–141`). Separately, on the **same paid success path**, **`senderUid`** gates whether `shared/{sessionKey}` includes `senderUid` and whether `users/{senderUid}/letters/{sessionKey}` is written (`api/verify-payment.js:632–641`, `654–661`). Those are **not** inside the email helper.
- **Founder success path** returns `200` with `sessionKey` / `shareSlug` **without** calling `sendLetterSealedNotification` (`api/verify-payment.js:359–412`).

### 6. Form/draft state for guests

- **During PREPARE:** `usePreparationPersistence` / `peekDraft` use **`vday_data_draft`** (`hooks/usePreparationPersistence.ts:4`, `152–173`, `182–184`).
- **Across post-PREPARE persistable stages:** `writeStage` merges **stage** into the same draft record when `PERSISTABLE_SENDER_STAGES` matches (`hooks/usePreparationPersistence.ts:206–227`; set includes `PAYMENT`, excludes `SHARE` — `App.tsx:128–135`, `491–492`).
- **Separate finalized snapshot:** **`vday_data`** for validated `CoupleData` (`App.tsx:94`, `148–165`, `1437–1446`).
- **Cleanup:** `clearPreparationDraft` removes **`vday_data_draft`** on payment success (`hooks/usePreparationPersistence.ts:266–272`; call site `App.tsx:1565–1567`). Invalid `vday_data` on read removes item (`App.tsx:155–157`).

### 7. Founder-code path data model

- **Applied in:** `api/create-order.js` when `founderCode` present — increments `founderCodes/{code}`, writes **`founderTokens/{token}`** (`api/create-order.js:97–174`).
- **Redeemed in:** `api/verify-payment.js` **`paymentMode === 'founder'`** branch — consumes token, writes **`shared/{sessionKey}`** with `paymentMode: 'founder'`, `paidAmount: 0`, `paymentId: founderId`, and **`payments/{founderId}`** (`api/verify-payment.js:363–384`).
- **Client:** `PaymentStage` sends `founderCode` to create-order, then `paymentMode`, `founderToken`, `coupleData` to verify (`components/PaymentStage.tsx:74–99`).
- **Bypass auth:** verify-payment founder branch does not require `getSessionUser` to succeed; **`senderUid`** optional on writes (`api/verify-payment.js:372`, `386–391`).
- **State names like `amountPaise` / `isFounderFlow`:** not found as client state flags in `PaymentStage.tsx`; founder path uses **`founderApproved`** / **`founderToken`** from API responses (`components/PaymentStage.tsx:84–88`, `91–98`). Server stores **`paidAmount: 0`** and **`paymentMode: 'founder'`** on shared payload (`api/verify-payment.js:369–371`).
- **Influencer audience identifier:** **No dedicated “recipient of founder code” profile** in code reviewed; redemption is **IP-rate-limited** invalid attempts (`api/create-order.js:43–60`, `78–87`) and tied to **anonymous** browser session unless the sender is signed in (`senderUid` optional).

## Architectural observations

- **Optional session cookie** is threaded through payment verification for **dashboard mirroring**, not for blocking fulfillment (`api/verify-payment.js:283–287`, `654–661`).
- **Email notification** is strictly **ancillary**: helper never throws; documented as non-blocking for HTTP (`api/verify-payment.js:67–90`, `691–693`).
- **Two localStorage namespaces** for creator state: **`vday_data_draft`** (debounced prep + stage) vs **`vday_data`** (validated post-refine snapshot) (`hooks/usePreparationPersistence.ts:4–8`; `App.tsx:94`).
- **Founder fulfillment** is a **separate branch** from paid Razorpay with **no** `sendLetterSealedNotification` invocation (`api/verify-payment.js:298–412` vs `433–715`).

## Open questions for the design phase

- **Operational recovery:** Whether support or internal tools can locate a letter from **Razorpay `paymentId`** / **`shared/{sessionKey}`** without a product UI change — not answered from frontend-only review.
- **Replay / `processing: true`:** Client handling of verify responses that return **`verified: false`** with **`processing: true`** (`api/verify-payment.js:547–552`) vs user-facing recovery — `PaymentStage` treats non-`verified` as failure (`components/PaymentStage.tsx:219–220`); full UX outcome not traced here.
- **Eid `receiverPhoneNumber`:** Whether this field is considered PII sufficient for trust artifacts or must remain receiver-scoped — only noted as present on `CoupleData` and Eid payload (`types.ts:129`; `App.tsx:1162–1166`).
